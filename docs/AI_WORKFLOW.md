# 我怎么和 AI 一起写代码

## 1. 我怎么给上下文

### 贴之前先说清四件事

- 当前在做什么（哪个功能、哪个端点）
- 已经做到哪一步（上次改了什么、现在什么状态）
- 这次要实现什么
- **怎样算成功**（跑通哪条路径、返回什么、日志里该出现什么）

不说第 4 条时，AI 会自己选一个它认为合理的实现，而那个实现往往跟我想的不一样。
这不是"它理解不了"，是"它替我做了决定"。

### 贴的时候：给完整的文件或完整的输出，不裁剪

- **代码给整份文件，不给片段。** 片段会让它猜上下文，猜错的地方我要花更多时间纠正。
- **报错贴完整 traceback + 完整控制台输出。** 因为我不知道哪一行重要——裁剪就等于我替 AI 做了判断，而我没有资格做这个判断。
- 实例：只贴"报错那一行"的话，就看不到 `delay=9.47s`，也就看不出第 3 次重试还在白等。

### 一次只让它改一个文件里、当前开发步骤涉及的那部分

改动面一大，出错时我不知道是哪一处引起的。

### 我很少说"帮我写个功能"

因为不说验收标准，AI 会自己设定目标。
我现在的做法是：**先让它只读不写地审一遍，我判断完再让它动手。**

### 效果最好的一次：把 `app.py` 收束到 `api/` 目录

1. 先说明：我在把 Streamlit 版的功能搬进 `api/`，现在工具定义有两份，目标是一份
2. **让 AI 只审查**：找出重复定义、没有被引用的代码块——这一阶段它不改代码
3. 我自己判断哪些该删（有的函数虽然重复，但语义不同）
4. 手动收束
5. 再让 AI 复审一遍

**有效的原因：第一阶段它只读不写，我保留了"哪些该删"的决定权。**
如果我一开始就说"帮我收束"，它会直接改，我就失去了判断的机会。副作用的代码块，收束完之后手动微调，再让ai复审

## 2. 我从不省的验证

### 每次改完都做的三件

**① 先确认「能加载」，再谈「跑得对」**

```bash
python -c "import api.main; print('ok')"
```

这一步抓的是 `NameError` / `ImportError` / 循环依赖。
今天所有崩溃都在这一步暴露：`DB_URL` 从错误的模块导入、`RETRYABLE` 里四个异常名没导入、`OpenAI` 没导入。

**能加载不等于能跑，但加载不了就不必往下测。**

---

**② 跑真实请求，不看代码「像不像对的」**

```bash
curl -i -m 90 -X POST http://127.0.0.1:8000/chat \
  -H "Content-Type: application/json" -d '{"question":"现在几点"}'
```

一次看三样：

- **HTTP 状态码**（200 / 404 / 504 —— 状态码本身就说明责任在哪一方）
- **响应体**（能不能让调用方决定下一步）
- **日志那一行 JSON**（`latency_ms` / `steps` / `tools` / `finish_reason`）

**我不拿「代码看起来没问题」当验收。**

---

**③ 刻意造坏输入，专走异常分支**

做法：读完代码的 `if` / `except` 分支，列出「正常分支 + 异常分支」的用例清单（清单我让 AI 生成，**跑和判断是我做的**），逐个跑。

造过的坏输入：

| 输入 | 期望 |
|---|---|
| `DEEPSEEK_BASE_URL=http://127.0.0.1:9` | 504，不挂住，服务存活 |
| 不存在的 `session_id` | 404 |
| 上传非 `.md` / 非 UTF-8 文件 | 400 |
| 语料外的问题（天气、React） | `sources` 为空 + 明确拒答 |
| 让模型读 `../../.env` | `PATH_DENIED`，且是代码拦的，不是模型拒绝的 |

**判据：异常分支的返回，能不能让调用方采取行动？**
说「服务器错误」不行（调用方不知道要不要重试），说「上游超时，请稍后重试」才行。

---

### 改动面大的时候，额外做两件

**④ 把「受影响的参数」单独拎出来逐个复查**

AI 给的方案改动大时，我不直接接受——先列出这次改动会碰到哪些已有的参数、配置、调用方。

实例：把 `client` 从 `main.py` 搬到 `llm.py`，受影响的至少有 `DB_URL`（导入来源变了）、`RETRYABLE`（异常名没跟着搬）、`tools`（新函数要不要传）——**三处全崩了，靠 ① 那条命令一次性抓出来。**

---

**⑤ 数字不信 AI，自己测**

| AI 的方案 | 它说的收益 | 我测出来的 | 决定 |
|---|---|---|---|
| 加 rerank 提升检索 | 相关性更高 | 20 题：top1 没涨，recall@3 从 20 掉到 19 | 关闭 |
| 换云端 embedding | 省 330MB 内存 | 17/20 → 16/20，延迟 50ms → 244ms | 不换 |
| 换 ONNX 量化 | 省 282MB、快 2 倍 | 17/20 → **14/20** | 不换 |

**判据：凡是 AI 说「会更快 / 更准 / 更省」，我就用评测集跑一遍。**
**同一个评测集，跑前跑后各一次，数字不会骗人。**

## 3. AI 给的方案，我用什么否掉

### 三条被数据否掉的

| AI 的方案 | 它当时为什么看起来合理 | 我否掉的依据 | 结果 |
|---|---|---|---|
| 加 rerank 提升检索 | cross-encoder 精度更高是常识；**5 题小样本上确实有效**——gap 从 0.007 涨到 0.112 | 扩到 20 题：top1 没涨，recall@3 从 20 掉到 19，`04_进程同步` 被挤出前 3 | 关闭，`ENABLE_RERANK=0` |
| 换云端 embedding（省内存） | 省 330MB。当时 ECS 只剩 336MB 可用，**这等于救命** | A/B 同集：17/20 → 16/20，recall@3 20 → 19，延迟 50ms → 244ms | 不换；改为**加内存**到 4G |
| 换 ONNX 量化（省内存） | 省 282MB、单条快 2 倍、冷启动 118s → 1.7s，**三项全赢** | A/B 同集：17/20 → **14/20**，且出现跨主题错位（`13_ARP` → `10_进程间通信`） | 不换，保留 torch |

**注意第一行的细节：5 题时它是有效的。**
**小样本会给出虚假信心——这是这三次实验教给我的同一件事。**

### 判据分两种，因为两种场景的答案不同

**① 有评测集 → 用数字，不讨论「感觉」**

19/20 和 20/20 这种差别肉眼看不出来，只能测。
**任何"更准/更快/更省"的主张，都在同一个评测集上跑前后对照。**

**② 没有评测集 → 问「如果这个方案错了，谁会先发现？」**

- 答「用户会发现」→ 太晚，要么加测试，要么否掉
- 答「日志里会出现异常值」→ 可以接受
- 答「没人会发现」→ **否掉，或者先加监控**

### 不是所有方案都要否掉，大部分是改造

| 方案 | 我的处理 | 为什么不是"接受"也不是"拒绝" |
|---|---|---|
| SDK 默认重试 2 次 | **保留思路，改参数**：`max_retries=0`，重试集中到我这一层 | SDK 的重试不看总预算、无法打日志——**思路对，位置不对** |
| 检索无命中就硬拒答 | **改造**：从「循环前 return」改成「`retrieved=[]` 继续进循环」 | 硬拒答本身对（省成本、不编造），但它挡死了 `get_time` / `query_chunks`——**策略对，边界画错了** |
## 4. 三次 AI 出错，错误是怎么被发现的

**先说明这一节的性质：这三个 bug 都不是我自己看出来的。**
记录它们的价值不在于显得厉害，而在于标出我现在的水平——以及两个月后回看时，能看出变了多少。

### 案例一：SDK 自己也在重试，我的退避白算了

- **现象**：超时测试耗时 14.6 秒，比我算的 6 秒多一倍多
- **我先做了什么**：直接把完整的控制台输出贴过去，没有提出假设
- **我最初的判断**：无——我不知道该怀疑哪里
- **提示级别**：L3 讲机制（L1 只说范围 / L2 指出锚点 / L3 讲机制 / 直接给答案）
- **找到的关键线索**：`Retrying request in 0.49 seconds (retry 1 of 2)` 这一句 —— 它带着 `retry 1 of 2` 这种格式，一看就不是我写的代码打的
- **真实原因**：`OpenAI()` 默认 `max_retries=2`，和外层的 3 次尝试叠加，实际发出 9 次请求
- **我的教训**：我加的机制必须能压住底层默认值。

### 案例二：最后一次重试失败，还白等了 9.47 秒

- **现象**：修完上一条后仍需 15.8 秒；打点日志显示 `attempt=2` 也算了 `delay=9.47s`
- **我先做了什么**：贴了 `[retry]` 三行日志
- **我最初的判断**：无
- **提示级别**：L2
- **找到的关键线索**：`已用=6.22s` 和 `latency_ms=15785` 对不上 —— 6.22 + 9.47 ≈ 15.7，说明那 9.47 秒真的睡了
- **真实原因**：`if monotonic() + delay > deadline` 只判「预算够不够」，没判「还有没有下一次」
- **我的教训**：「能继续」和「该继续」是两件事。

### 案例三：加一行日志，把 504 变成了 500

- **现象**：加完打点后请求返回 500，而不是原来的 504
- **我先做了什么**：贴了代码片段
- **我最初的判断**：无
- **提示级别**：L3
- **找到的关键线索**：`took` 出现在函数签名里（`took=None`），但循环体内从来没被赋值
- **真实原因**：`f"{None:.2f}"` 抛 `TypeError`，而它抛在 `except` 块内部，不被 `RETRYABLE` 接住，一路冒到外层变成 500——**同时把原始异常也吞掉了**
- **我的教训**：打点/日志代码本身会成为新的失败源。

---

### 这一节的三个共同点

1. **我都先把完整输出贴过去，没有裁剪** —— 这是唯一每次都做对的事
2. **我最初都没有假设** —— 这正是不足之处
3. **三个都必须靠打点/对账才能看见** —— 它们都不报错，只是行为不对

**下一步要练的：看到输出先写下「我猜是 X」，再贴。**

### 三个案例的同一个来源

三次都是**在同一个位置出错**：我新加了一层机制，它和已有的机制冲突。

| 案例 | 我新加的 | 和谁冲突 |
|---|---|---|
| 一 | 外层重试 | SDK 内置的 `max_retries=2` |
| 二 | 总预算判断 | `range(max_attempts)` 的次数上限 |
| 三 | 打点日志 | `except` 块的异常传播 |

**所以以后的检查点变成一句话：每新增一层，先问「它和已有的哪一层做同一件事」。**

**做同一件事的两层，迟早会打架；而且都不报错，只是行为不对。**

## 一句话总结

我的角色不是「让 AI 写代码」，是验证和否决：现在我做得到「跑通 + 造失败」，还在练「不看提示就定位问题」。
