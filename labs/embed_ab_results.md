# Embedding 方案对照实验（2026-11-17）

**目的**：项目 A 的 `/chat` 进程约 392 MB，其中 ~500 MB 峰值来自 torch + `bge-small-zh-v1.5`
（2 核 2G 的 ECS 上，这决定了能否再并行跑第二个服务）。
本实验回答一个问题：**换成更轻的 embedding 来源，检索质量会掉多少？**

**结论先说**：三条省内存的路径都掉点，掉点幅度与省下的内存不成正比，**最终保留本地 torch 模型**。

---

## 方法

| 项 | 设置 |
|---|---|
| 语料 | `notes/` 20 篇 → `head` 切分 59 块（与生产一致） |
| 评测集 | `labs/eval_set.json` 20 题，每题唯一最佳答案文件 |
| 指标 | `top1`（第一名是否命中）、`recall@3`（前三是否包含）、`margin = sim₁ - sim₂` |
| 公平性 | 三种方案**都**用「文档和查询」在同一向量空间内计算余弦；不混用不同来源的向量 |
| 脚本 | `labs/embed_ab.py`（API 方案）、`/tmp/onnx_20q.py`（ONNX 方案，可移植为 `labs/`） |

---

## 结果

| 方案 | top1 | recall@3 | margin<0.01 题数 | 进程 RSS | 单条延迟 |
|---|---|---|---|---|---|
| **torch + bge-small-zh-v1.5（现用）** | **17/20** | **20/20** | 8 | 510 MB | ~50 ms |
| 阿里云百炼 `text-embedding-v3`（512 维） | 16/20 | 19/20 | — | 0（远端） | ~244 ms |
| ONNX int8（fastembed，`-onnx-Q`） | **14/20** | 20/20 | **10** | **228 MB** | **19–21 ms** |

**torch 数据来自 11-10 的最终评测；后两者为 11-17 实测。**

## 逐题差异（只列未命中）

| 问题 | 期望 | torch | 百炼 API | ONNX int8 |
|---|---|---|---|---|
| 读写文件为什么让操作系统代劳 | `01_系统调用` | ✓ | ❌ `02_进程` | ❌ `02_进程` |
| 两个进程同时加一结果对不上 | `04_进程同步` | ✓ | ❌ `02_进程` | ✓ |
| 内存不够用时系统会怎么办 | `07_虚拟内存` | ❌ `06_内存` | ❌ `05_死锁` | ❌ `06_内存` |
| 缓冲为什么要先攒一块 | `09_IO管理` | ❌ `08_文件系统` | ✓ | ❌ `07_虚拟内存` |
| 同一根线发数据怎么知道撞上了 | `12_CSMA-CD` | ❌ `17_TCP` | ✓ | ❌ `17_TCP` |
| 怎么知道对方的 MAC 地址 | `13_ARP` | ✓ | ✓ | ❌ **`10_进程间通信`** |
| RIP 和 OSPF 差在哪 | `15_路由协议` | ✓ | ✓ | ❌ `13_ARP` |
| NAT 怎么区分内网设备 | `20_NAT` | ✓ | ❌ `11_网络概述`（**前三都没有**） | ✓ |

**读法**：

- **百炼 API** 的错法多是「跑到相邻主题」（`01→02`、`07→05`），属于**语义粒度变粗**；
  但出现了一次 `recall@3` 缺失（NAT 完全掉出前三），是硬伤。
- **ONNX int8** 出现了 **`13_ARP → 10_进程间通信`** 这种**跨主题错位**，说明量化后语义区分度劣化得更厉害；
  它的 `margin<0.01` 有 10 题（torch 8 题），排序更脆。

## 成本与取舍

| 维度 | torch（现方案） | 百炼 API | ONNX int8 |
|---|---|---|---|
| 内存 | 510 MB | 0 | **228 MB** |
| 冷启动 | ~118 s（加载权重） | ~0 | **1.7 s** |
| 检索延迟 | ~50 ms | ~244 ms | **~20 ms** |
| 镜像体积 | ~900 MB（含 torch） | ~200 MB | ~250 MB |
| 离线可用 | ✅ | ❌ 断网即不可用 | ✅ |
| 数据出网 | ❌ | ⚠️ 笔记内容发给服务商 | ❌ |
| **top1** | **17/20** | 16/20 | **14/20** |

**权衡点**：省 280–500 MB 内存 ≠ 值得掉 1–3 个 top1 命中。
**top1 命中率是本项目的核心指标**（也是 README/简历里的第一条数字），不能为了部署便利牺牲它。

---

## 决策

**保留 torch + `bge-small-zh-v1.5`。**

**若确实需要给第二个服务腾内存，选择「加内存到 4G」而不是「换 embedding」**——
加内存**完全不改变检索质量**，而换 embedding 会直接拉低项目最核心的评测数字。

**备选（未采用但值得记录）**：fp32 ONNX（自己用 `optimum-cli export onnx` 导出）
理论上能保持精度并省 ~160 MB，但需要临时安装 torch 做导出，且收益小于加内存，投入产出比不划算。

---

## 局限

- 评测集只有 20 题，1 题的差异 ≈ 5 个百分点，**统计意义弱**；结论方向可信，具体幅度不宜过度解读。
- torch 的单条延迟是估算（未单独计时），另两者为实测。
- ONNX 用的是 **int8 量化版**（fastembed 只提供该版本）；结论是「量化 ONNX 掉点」，不等于「ONNX 本身掉点」。
- 三种方案各只测了一轮，未做多次运行的方差分析。

## 复现

```bash
# 百炼 API 方案
cd /opt/ai-partner && set -a && . ./.env && set +a && .venv/bin/python labs/embed_ab.py

# ONNX 方案（独立 venv，避免污染生产依赖）
python3 -m venv /opt/onnxtest && . /opt/onnxtest/bin/activate
pip install fastembed numpy psycopg
HF_ENDPOINT=https://hf-mirror.com python /tmp/onnx_20q.py
```

**注意**：2 核 2G 上跑 ONNX 方案前先 `systemctl stop aipartner`，
否则 ONNX 的 CPU arena 峰值会触发 OOM killer（实测曾杀掉同机 gateway 进程）。
